# Environments and the Toy Evaluator

In eval-expr, evaluating ((lambda (x) (+ x 1)) 5) reaches the default application branch. It evaluates the operator (lambda (x)(+ x 1)) into a closure using the lambda branch where (make-closure params body env) captures the environment in which the lambda was defined. This then evaluates the argument 5 and passes the closure to apply-closure, which (extend-env params args env) then binds x to 5 in the closure's captured environment, implementing lexical scoping.

If we traced say `(let ((x 2)) (let ((f (lambda (y) (+ x y)))) (let ((x 100)) (f 1))))` through `eval-expr`, the first `let` will extend the empty environment to `((x . 2))`, then the second `let` evaluates its initializer, a `lambda` form, in that environment. The `lambda` branch of `eval-expr` runs `(make-closure params body env)`, which is the line that captures the defining environment. `env` now holds only `((x . 2))`, so the closure is `(:closure (y) (+ x y) ((x . 2)))`. The later `x` bound to 100 sits in a different environment that the closure never saw. Because `apply-closure` extends this saved environment with `y` bound to 1, the body `(+ x y)` finds `x` as 2 and returns 3, even though `f` is called where `x` is 100.

If application joined the arguments, to the caller's environment, the language would use dynamic scoping instead. Specifically, `apply-closure` would call `(extend-env params args env)` with the `env` of whoever calls the function, not the `env` saved by `make-closure`. In the scope-discrimination case, `(f 1)` runs inside the innermost `let`, where the caller's environment is `((x . 100) (x . 2))`. After `y` is bound to 1, `lookup` finds the first `x`, which is 100, so the case would return 101 instead of 3. 

CLISP needs funcall since it is a Lisp-2, which keeps variables and functions in separate namespaces. For the toy language, it is a Lisp-1 which means that variables and functions only share one namespace. In Lisp-2, a function stored in a variable cannot be called directly as an operator using that variable's name, while Lisp-1 variables can be called directly without funcall. In this context, in the `eval-expr`, the application branch evaluates the operator with `(eval-expr op env)` like a regular argument, so a variable bound to a closure works in operator position. In the host, `extend-env` has to write` #'cons` to hand mapcar the function, because CLISP keeps functions in a separate namespace.
